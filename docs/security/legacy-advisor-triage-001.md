## Canonical and governance boundary

Production source_entries, linguistic_evidence, source_artifacts and contributor_roles have RLS enabled and no anon/authenticated SELECT grant in inspected catalogs. reviewer_profiles permits authenticated SELECT with an own-user policy. contributors has client grants and RLS but no policy returned; table grants alone do not establish accessible rows. Do not add pilot identity metadata to legacy public rows to work around denial.

011/012 are not hosted. Their SQL and synthetic denial tests protect the private lexical and governance tables; existing legacy views do not automatically gain those fields. However service_role retains canonical SELECT, owners can bypass controls, privileged application exports can leak private data, and the existing concepts table has public compatibility metadata. The pilot must keep sensitive text/identity references out of public concepts, legacy dictionaries, submissions, logs and analytics. No global concept creation/revision is supported in 012 policy 001.

New operational risks are the introduction of individual research logins, private proposal/evidence snapshots, broad evidence locks and authority provisioning. Require secure credentials/TLS, least privilege, private storage and log handling, revocation tests, exact-scope independence, and backup/audit custody. They are distinct from the 45 historical advisor findings; advisor silence is not proof of safe operation. A failed outer transaction/disconnect cannot preserve a private failure event; infrastructure logs need an approved privacy-conscious audit strategy.

## Separate hardening implementation plan

1. Security owner inventories actual hosted grants, API exposure, RPCs, view dependencies, service exports and affected data classifications in both environments. Preserve schema/grant baseline and recovery plan; determine existing consumer contracts.
2. Produce a separate versioned migration PR for restricted legacy writes/reads, scoped RLS and view behavior. Do not drop/recreate tables or silently break public consumers. Address submissions and sensitive operational/contributor paths first. Keep extension relocation a separately assessed compatibility change.
3. Replay historical and new migrations in isolation. Run full source/evidence/canonical/portal regressions, SQL and HTTP role-based denial tests, cross-user/variety tests, candidate-read compatibility, advisor comparison and query-plan checks. Verify no restricted data through views/RPCs/logs/exports. Demonstrate rollback/recovery.
4. Obtain independent security review and explicit staging deployment authorization. Recheck hosted drift, apply only approved migrations, then verify staged flows before any separately authorized production rollout.
5. Before real pilot data, remediate high-risk paths or document tested technical isolation preventing pilot data/identity entry and downstream contamination, approved by the security owner. A statement that findings are historical is insufficient. Low-risk performance findings can be scheduled with a recorded disposition; no blanket requirement to change every policy for this preparation.

Current decision: security/dependency gate remains closed. No mitigation has been applied or independently accepted.
