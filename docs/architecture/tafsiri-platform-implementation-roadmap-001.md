## Ordering and parallel development

M2 and M3 can proceed as separate reviewed implementation changes after M1. M4–M6 can use synthetic fixtures while hardening is in progress. M9/M10 can implement against M8 mock contracts but cannot serve a real model before M8 approval gates exist. Synthetic integration tests accumulate throughout; M11 is the complete system acceptance gate, not the first time components are tested. This ordering avoids requiring language recruitment or corpus acquisition to validate software.

The 013 compatibility guard rejects 012 proposals using new LANGUAGE/MULTILINGUAL evidence or a source version with new scope assertions. Before M12 promotes such inputs, a separately reviewed promotion policy revision must bind those assertions into the frozen digest and authority checks. Do not disable the guard. Earlier unchanged sources remain subject to existing 012 policy and their independent readiness gates.

## Software readiness versus real-data readiness

Software readiness requires approved design, implementation, denial-path tests, reproducibility, restoration, deployment controls and operating ownership. It can be demonstrated entirely with labeled synthetic fixtures; synthetic vocabulary is never authentic linguistic evidence.

Real-data readiness separately requires acquired and authenticated source bytes, complete entry/import/artifact lineage, resolved exact scope, current explicit permitted uses/consent, qualification evidence, independent reviewers/approvers, approved protocol, protected storage and authorized environment. The Luwanga pilot documents currently record no eligible lexical promotion packet; this architecture does not reopen corpus collection or repair permissions. Other languages use the same checklist and infrastructure rather than parallel projects.

Research training readiness does not imply research redistribution, commercial clearance or service readiness. Production additionally requires a cleared model, scope-specific evaluation thresholds, approved SLO/resource budgets, retention/region policy, billing reconciliation, incident ownership and explicit deployment approval. Each milestone's implementation PR must name its acceptance evidence, unresolved limitations and rollback/recovery procedure.

## Data Studio amendment: collection before a corpus

Insert M2C (Data Studio architecture and synthetic MVP) after M1; it can run alongside M2/M3 without real data. Deliver a private contributor module, proposed-language projects, consented drafts/uploads, admin triage, offline AI proposals and blocked registration packets. Acceptance requires a hypothetical language with no corpus, immutable original submission, own-user isolation and no automatic reviewer/canonical/training authorization. Test forged identities, retries, private storage, consent, withdrawal, malformed files and unsupported providers. Complexity L. Deployment stays closed pending independent security review, explicit approval and real-data readiness. M4 consumes authorized Studio intake through existing source registration; M12 can begin governed collection without an existing dataset. The institutional extension adds organization onboarding, scoped collaboration and an optional OpenAI adapter; live external activation and offline sync remain separate later gates.
