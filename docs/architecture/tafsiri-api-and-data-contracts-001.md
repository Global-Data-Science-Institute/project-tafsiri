# Tafsiri API and data contracts 001

Status: authoritative catalog for future integration. Existing 012/013 interfaces retain their implemented contracts. New schemas are design artifacts, not working APIs or deployed database objects. [Reference architecture](tafsiri-platform-reference-architecture-001.md) assigns domain ownership.

## Common conventions

Use exact `{kind: language|variety, id: UUID}` scope. IDs are environment-local; cross-environment transport needs an explicitly reviewed mapping, never names, aliases or parent inference. Orthography keys identify immutable versions. Wire contract major versions change for incompatible semantics; additive optional fields require compatibility review, and strict consumers must negotiate their supported version before receiving extensions. Signed payloads and immutable manifests never change in place. Unknown versions fail closed.

Every command carries a request/correlation ID, authenticated principal, idempotency key where a mutation can retry, and expected version for optimistic concurrency. Client actor/tenant IDs are not authority. Hashes are lowercase SHA-256 of exact declared bytes; a hash is not rights validation. Signed payload serialization rejects duplicate keys, nonfinite numbers and ambiguous encodings. Approval `subject_sha256` binds the frozen review-subject projection (content, scope, lineage and policy inputs, excluding approval/signature fields); the final manifest digest additionally covers attached approvals. Document the projection/serialization version with each protocol to avoid circular self-hashing. 012 PostgreSQL JSONB digests and 013 sorted compact JSON profile digests remain distinct existing protocols, not interchangeable with these byte hashes.

Errors use request ID, stable code, safe message and retryable flag. HTTP: 400 malformed, 401 unauthenticated, 403 operation denied, 404 absent/inaccessible object, 409 conflicting retry/stale version, 422 unsupported scope or invalid semantics, 429 quota/rate limit with Retry-After, 503 unavailable capacity or eligibility authority. Private source existence, permission narratives and reviewer identities are never disclosed in errors. Internal jobs additionally record failure stage/attempt privately. SQL RPCs retain their current error behavior; do not retrofit HTTP semantics into them in this architecture.

## Machine-readable specifications

[Platform JSON Schema](contracts/tafsiri-platform-v1.schema.json) uses Draft 2020-12 named `$defs`: Scope, Direction, Artifact, Approval, Lineage, Split, DatasetManifest, TrainingJob, ExperimentResult, EvaluationReport, ModelRecord, CommercialRelease, SignatureEnvelope, TranslationRequest/Response, UsageEvent, BillingEvent and Error. Validate the selected named definition, not the definition-only root. UUID/date-time format checks must be enabled by consumers. These schemas define structural minimums; authorization, referential integrity, timestamps, state transitions and cross-record semantics require the catalog's server checks.

Semantic constraints include: exactly one train/dev/test split each for training datasets; disjoint groups and frozen test exclusions; valid-from before valid-until; approval subject hashes match the specified review projection; every lineage item maps to content/index records; current rights checked independently of the cited references; successful runs have verified output artifacts; failed/cancelled results have failure codes; evaluations bind the exact model and complete required strata; uncertainty has no translated text; billable events require translated outcome. `canonical_revision_ids=[]` is allowed only for explicitly approved noncanonical research tasks, never a canonical lexical dataset. Optional consent references require a recorded determination that consent does not apply, not an unchecked omission.

[Cloud OpenAPI 3.1](contracts/tafsiri-cloud-v1.openapi.json) describes only planned public/customer operations. No server URL is advertised. API keys use `X-Tafsiri-Key`; key management requires an authenticated human session with organization administrator authority, not another inference key. Browser/session integration must use its separately approved CSRF/token handling. Scope policy is recorded as `x-required-scope`, since API-key security schemes do not define OAuth scopes. List cursors are opaque, tenant-bound and expire; usage periods are bounded and UTC; key creation cannot exceed the caller's entitlements. Secret responses use no-store and never appear in list responses. Catalog responses contain approved Cloud projections, not private registry assertions.

## Compatibility and contract verification

Producer/consumer suites must reject unknown versions, duplicate JSON keys, extra fields, malformed digests, invalid enums and scope ambiguities; verify current reference/rights state separately. Test conflicting idempotency bodies, stale worker fencing, cross-project/tenant IDs, altered manifests and revoked approvals. Contract fixtures use synthetic identifiers/text, never invented Luhya presented as real data. Consumer compatibility and denied-path tests precede rollout; architecture schema validation alone proves no runtime behavior.

## Data Studio amendment

[Collection and annotation contracts](tafsiri-data-studio-contracts-001.md) add versioned private collection commands, language proposals, original representations, independent consent assertions, upload quarantine, AI suggestion provenance and blocked registration packets. Studio owns collection origin; existing source/evidence/canonical contracts remain authoritative after authorized handoff. Acceptance for intake is not verification. No API creates an approved language, reviewer task, canonical record or training permission automatically.
